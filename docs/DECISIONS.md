# STRUCTURA — Архітектурні рішення

Формат: рішення · причина · наслідки.

**D-001 — Єдина БД і спільні сутності.** Усі модулі посилаються на `companies`, `construction_objects`, `profiles`,
`company_members`, `object_members`, `activity_log`. Власних «користувачів/компаній/обʼєктів» у модулях немає.
*Наслідок:* нові таблиці модулів мають `company_id` і (за потреби) складений FK `(object_id, company_id)`.

**D-002 — Складені зовнішні ключі `(object_id, company_id)`.** `construction_objects` має `unique(id, company_id)`;
`object_members`, `invitations`, `activity_log` посилаються на пару. *Причина:* захист від підміни `company_id`/`object_id`
на рівні схеми, а не лише політик. *Перевірено тестом.*

**D-003 — Усі чутливі записи — через RPC `SECURITY DEFINER`, прямі INSERT/DELETE заборонені.** Створення компанії/обʼєкта,
членство, ролі, запрошення, журнал. *Причина:* атомарність (компанія + власник), неможливість самопризначення ролей,
уникнення пасток `INSERT … RETURNING` + RLS. *Наслідок:* клієнт викликає `supabase.rpc(...)`; помилки мапляться за текстом (див. DATABASE.md).

**D-004 — Привілеї на рівні стовпців.** `UPDATE` дозволено лише безпечним стовпцям; `token_hash` не читається клієнтами.
*Причина:* RLS не обмежує, які стовпці змінюються.

**D-005 — Видимість обʼєктів.** owner/admin компанії бачать усі обʼєкти компанії; інші ролі — лише обʼєкти, де вони в
`object_members`. Зовнішні учасники (замовник, посередник) — не члени компанії, бачать лише свої обʼєкти.
*Альтернатива (всі члени бачать усі обʼєкти) відхилена як менш безпечна за замовчуванням.*

**D-006 — Одна роль користувача на обʼєкті на Етапі 1** (`unique(object_id, user_id)`). Якщо знадобиться кілька (напр.,
працівник + відповідальний за інструмент на одному обʼєкті) — міграція на `unique(object_id, user_id, role)` разом із перегляд функцій.
Різні ролі на різних обʼєктах підтримуються.

**D-007 — `super_admin` зарезервований.** Значення є, але політики не дають йому неявного доступу до даних компаній
(мінімум привілеїв). Службовий доступ — окремим рішенням пізніше (напр., аудитований RPC).

**D-008 — Власник призначається лише через `create_company`.** Один `owner` на компанію (частковий унікальний індекс).
Роль `owner` не можна призначити/змінити через RPC; передача володіння — окрема майбутня операція. Імена/email власників
у коді не зашиваються (перший керівник отримує права, зареєструвавшись і створивши компанію).

**D-009 — Токени запрошень.** 256 біт випадковості, у БД лише SHA-256 хеш, показуються один раз; повторна видача
ротує токен. Прийняття вимагає підтвердженого email, що збігається з адресою запрошення. Існуюче членство не перезаписується.
Доставка листів відокремлена й **не реалізована** (`delivery_status = 'not_sent'`).

**D-010 — Журнал подій append-only,** запис лише через внутрішню `log_activity` (клієнтам недоступна), поле `module`
для майбутніх модулів.

**D-011 — Не фіксувати CAD-схему заздалегідь.** Геометрична модель Measure проєктується на Етапі 2 після перевірки
математики; зараз лише вимоги (площа ≠ обсяг робіт, поріг 0,60 м) у `MASTER_PLAN.md`.

**D-012 — Грошові значення (Workforce):** `numeric`, не float; захист від подвійного нарахування — унікальним обмеженням у БД.

**D-013 — Видалення обʼєктів заборонене;** замість нього статус `archived` (+`archived_at`).

**D-014 — SQL-тести на «чистому» PostgreSQL із шимом Supabase** (`supabase/tests/_local_supabase_shim.sql`) як тимчасова
міра, доки немає доступу до Supabase CLI/проєкту. Шим НЕ замінює перевірку на реальному Supabase (TESTING.md).

**D-015 — Геометрія в мм.** Єдина внутрішня одиниця — міліметр; `display_units` лише для відображення/введення. Див. `ARCHITECTURE.md`, розділ 7.

**D-016 — Права Measure.** Редагують: owner/admin компанії та на обʼєкті `object_manager`, `foreman`, `surveyor`, `designer`.
`worker` — лише перегляд. Видаляти проєкти: owner/admin та `object_manager`. Замовник/посередник бачать проєкт лише при `client_visible = true`
і ніколи не редагують. Члени компанії без призначення на обʼєкт проєктів не бачать (узгоджено з D-005).

**D-017 — Область дочірніх записів визначає сервер.** `company_id`, `project_id`, `sort_order` поверхів/приміщень підставляються тригером
з батьківського запису, клієнт їх не передає (привілеї стовпців) — захист від підміни разом із складеними FK.

**D-018 — Оптимістична конкуренція через `version`** (тригер збільшує, клієнт перевіряє `where version = ?`). Для геометрії 2.2 буде пакетна
серверна операція з тією ж логікою.

**D-019 — Площі в `measurement_rooms` немає.** Не зберігати вигадану або проміжну площу; площа — похідна від геометрії замкненого контуру (2.3).
